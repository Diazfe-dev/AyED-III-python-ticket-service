## Decisiones (y por qué)

| Fecha | Decisión | Por qué |
|-------|----------|---------|
| 2026-11-09 | Python 3.12 + Flask + SQLite | Stack lo más simple posible para un TP; SQLite no necesita servidor. |
| 2026-11-09 | SQLAlchemy 2.0 como ORM (puro, sin Flask-SQLAlchemy) | Abstrae la base sin escribir SQL a mano. Al no usar Flask-SQLAlchemy, el dominio no depende de Flask y se testea sin levantar la app. |
| 2026-11-09 | Las entidades de dominio son también los modelos ORM | Es lo más simple para el alcance del TP. Costo: el dominio queda acoplado a SQLAlchemy. Se descartó separar dominio puro con mapeo imperativo porque duplica clases. |
| 2026-11-09 | Sin Alembic; esquema con `create_all()` | Menos dependencias. Se revisa si el esquema empieza a cambiar seguido. |
| 2026-11-09 | Patrón State para el ticket, guardando solo `state_name` en la base | Respeta el diagrama de clases sin convertir los estados en tablas. |
| 2026-11-09 | Patrón Strategy para notificaciones | Agregar un canal nuevo es sumar una clase, no un `if`. |
| 2026-11-09 | Inmutabilidad de hitos con listeners del ORM + triggers de SQLite | RNF 5: protege el historial también ante SQL directo, no solo desde el ORM. |
| 2026-11-09 | Ticket ajeno → 404 (no 403) | RNF 4: no confirmar la existencia de tickets de otros clientes. |
| 2026-11-09 | Reloj inyectable en services y dominio | RNF 6: los timestamps de auditoría se pueden testear de forma determinística. |
| 2026-11-09 | `pytest` + `ruff`, cobertura mínima del 90 % | RNF 1 (TDD) y un solo tool para lint y formato. Pendiente de confirmación por el equipo. |
| 2026-11-09 | Requerimientos funcionales descompuestos en specs con sintaxis EARS, en `specs/` | Frases atómicas y verificables que se traducen 1 a 1 en tests, lo que facilita el TDD (RNF 1). Cada test referencia el ID de la spec. |
| 2026-11-09 | Specs en español con palabras clave EARS en español (Cuando, Mientras, Si … entonces, Donde) | Coherencia con `REQUERIMIENTOS.md`. El código y los tests siguen en inglés. |

## Errores a evitar

- No usar `frozen=True` de dataclass en entidades mapeadas por SQLAlchemy: el ORM necesita poder setear atributos. La inmutabilidad de hitos se resuelve con listeners y triggers.
- No olvidar `PRAGMA foreign_keys = ON` en cada conexión: SQLite trae las claves foráneas desactivadas por defecto.
- No usar la API legacy de SQLAlchemy (`session.query()`, `Column` suelta).
- No cambiar el estado del ticket asignando el atributo directamente: siempre a través del objeto `State`, para que quede el `StateChange`.
- No filtrar los tickets por dueño solo en la vista: el filtro va en el service.
- No implementar specs que dependan de preguntas abiertas sin resolver.
- No escribir specs con dos comportamientos en una sola frase: rompe la trazabilidad spec → test.
- En EARS no se escribe "deberá no …": un comportamiento negativo se expresa con el patrón **Si … entonces** (pasó con SPEC-NTF-11).
- No editar `Diagrama.drawio` a mano sobre el XML: usar un script con `xml.etree` y validar que el archivo se pueda parsear. Después de cualquier cambio, reexportar los `.jpg` desde draw.io. (Histórico: ahora los diagramas son Mermaid.)
- En los bloques Mermaid no usar `;` ni `#` dentro de los mensajes (cortan la sentencia) y evitar `&`. Mantener balanceados los bloques `alt`/`opt` con su `end`.
- Un comando de CLI agregado con `app.cli.add_command` necesita `@with_appcontext` para usar `current_app`; si no, falla con "Working outside of application context" (pasó con `init-db`).
- En los tests, las respuestas del test client no siempre se cierran: servir archivos con `send_file` deja el archivo abierto (`ResourceWarning`). Para archivos chicos como el contrato, devolver `read_bytes()`. Además, cada app de test crea un engine en memoria que hay que liberar con `dispose()` al terminar.
- Las rutas de prueba se registran sobre la app del fixture (nueva por test), nunca en `create_app`, para que el test de sincronización con el contrato (SPEC-PLT-14) vea solo las rutas reales.
- PRs apilados: GitHub solo cambia la base de un PR a `dev` si se **borra** la rama base después del merge. Si no, el PR se mergea en la rama intermedia y nunca llega a `dev` (pasó el 2026-11-10 con #2 y #3, que se reemplazaron por #4 y #5). Antes de mergear, cambiar la base del PR siguiente a `dev`, o borrar la rama mergeada.
- El archivo de memoria se llama `MEMORY.md`, en mayúsculas. GitHub distingue mayúsculas en los links aunque macOS no.
- No hacer una baja física de entidades con historial (usuarios, productos): usar `is_active`.
- No tomar el representante ni el estado inicial de los parámetros del request: el representante sale de la sesión y el estado lo fija el dominio.
- Un test de integración que puede tocar la base tiene que pedir el fixture `schema`. Sin él, la fase roja falla por `no such table` y no por el comportamiento (pasó con el test de guarda TC-USR-16d al quitar un decorador para verlo fallar).
- Los defaults de columna (`default=True`, `default="mail"`) solo se aplican al insertar: en un objeto transitorio valen `None`. Si el service o un test necesita el valor antes del flush, asignarlo explícitamente.
- No editar `docs/openapi.json` pegando texto: un corchete de más deja el JSON inválido. Cargarlo, modificarlo como objeto y volver a escribirlo con el mismo formato (indentación de 2 y listas de escalares en una línea).
- Un hasher falso que compara strings enmascara errores de tipo que werkzeug sí lanzaría (pasó con TC-USR-25c y una contraseña numérica): cubrir esos casos también con un test de integración.
- No recibir valores del JSON sin chequear el tipo: un `name` numérico o un `preferred_channel` lista romperían con `AttributeError` o `TypeError` (500). El service los marca como `invalid`.
- Un test de "la base rechaza la baja" tiene que mirar la causa del error: sin `passive_deletes="all"`, el ORM pone la FK en `NULL` antes del `DELETE` y el `IntegrityError` de `NOT NULL` también se traduce a `CategoryInUseError`, así que el test pasaba igual (TC-PTY-14c ahora exige `FOREIGN KEY` en `__cause__`). Probar los tests de este tipo quitando la línea que protegen.
- `sqlite3` lanza `OverflowError` (`500`) con un entero mayor que `2**63 - 1`, y el conversor `<int:...>` de Flask no tiene límite. El catálogo lo resuelve en los `get` de sus repositorios y `01-users` en `SqlAlchemyUserRepository.get` (SPEC-USR-26, 2026-11-10). Todo `get` por id de un área nueva necesita la misma guarda.
- No registrar un manejador de errores sobre `Exception`: el request queda "manejado", el teardown recibe `exc=None` y se pierde el rollback de SPEC-PLT-08; además convierte las `HTTPException` en `500`. El `500` genérico va sobre `InternalServerError`.
- Con `TESTING` (o `DEBUG`), Flask relanza las excepciones no manejadas y nunca llama al manejador del `500`. Para probarlo, usar `unpropagated_app` (`PROPAGATE_EXCEPTIONS: False`).
- `int(texto)` lanza `ValueError` con más de 4300 dígitos (límite de Python): validar ids que llegan como texto sin asumir que `isdigit()` alcanza.
- En un fake con diccionario, `dict.get(True)` encuentra la clave `1` (`True == 1` y tienen el mismo hash): los ids booleanos se rechazan antes de llegar al repositorio, y los tests con `True` tienen que esperar un `ValidationError`, no un `404`.
- Un caso que verifica a través de otro endpoint (TC-PTY-07d usa `GET /product-types`) depende de la task de ese endpoint: ordenar las tasks en consecuencia o verificar contra la base.
- Un test que importa una excepción nueva falla en la colección (`ImportError`) y no por el comportamiento. Crear primero la clase vacía y volver a correr para ver el rojo correcto (pasó con `DuplicateProductError` y `ProductNotFoundError`).
- Una fila nueva de `ERROR_RESPONSES` se prueba agregando primero la ruta y después la fila: si se agregan juntas, el test del endpoint falla por la ruta inexistente (`404` `not_found`) y nunca por la traducción. Con TC-PRD-17d se vio la excepción sin traducir antes de sumar la fila.
- Un test parametrizado no puede cubrir dos casos del test-plan: el docstring cita uno solo (`SPEC-X · TC-X`). Escribir un test por caso (pasó con TC-PRD-02b y 02c).
- Los scripts que editan archivos por texto exacto fallan después de `ruff format`, que reacomoda decoradores y llamadas: buscar el texto después de formatear, o editar antes de formatear.
